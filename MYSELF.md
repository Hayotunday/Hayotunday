# Myself

## Who I Am

I'm a software developer with **4+ years of experience** building web applications, business systems, APIs, and increasingly, blockchain applications.

My background is primarily in **full-stack development**, where I've worked across the frontend, backend, databases, APIs, authentication, third-party integrations, deployment, and the practical problems that come with building software for real users.

Over time, I've become particularly interested in **blockchain and smart contract development**. My long-term goal is to specialize in **smart contract engineering and security**, while continuing to use my full-stack experience to build the applications and infrastructure that interact with those contracts.

I see these as complementary skills rather than separate careers.

---

## How I Think About Software

I enjoy building things, but I'm increasingly interested in understanding **why they work and how they can fail**.

Earlier in my development journey, getting an application working was often the main objective. With more experience, I've started paying much more attention to the decisions underneath the implementation:

* How should the system be structured?
* What happens when something goes wrong?
* Where are the security boundaries?
* How should data move through the system?
* What assumptions is the application making?
* Can the system scale beyond the initial use case?
* How can the code be tested beyond simply checking the happy path?

That mindset is one of the reasons smart contract security has become such an important direction for me.

Smart contracts are particularly interesting to me because the code is not simply responsible for producing the right output. It can control **assets, permissions, incentives, and irreversible state changes**.

That makes correctness and security much more important.

## What I Value as an Engineer

A few principles matter to me:

**Understand, don't just copy.**

If I use a library, framework, protocol, or pattern, I want to eventually understand what problem it solves and what assumptions it makes.

**Build for the actual problem.**

Good software isn't just technically impressive. It should solve the problem it was built to solve.

**Be honest about limitations.**

A prototype should be called a prototype. A learning project should be called a learning project. I would rather accurately describe what I built than exaggerate it.

**Keep learning.**

Technology changes quickly, and software engineering requires continuous learning. I expect my current skills and opinions to evolve as I gain more experience.

**Think about failure.**

The happy path is only part of the system. Good engineering also asks what happens when inputs are unexpected, dependencies fail, users behave maliciously, or assumptions turn out to be wrong.
